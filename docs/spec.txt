ТЕХНИЧЕСКОЕ ЗАДАНИЕ

Проект: portable Windows-приложение для ведения турниров и судейского подсчета результатов по Showdown для незрячих и слабовидящих пользователей
Версия документа: 1.0
Язык интерфейса первой версии: русский
Формат поставки результата по данному ТЗ: текстовый файл .txt

1. НАЗНАЧЕНИЕ ПРОЕКТА

Необходимо разработать desktop-приложение для Windows, предназначенное для:
- создания и ведения турниров по Showdown;
- регистрации и учета участников;
- создания матчей и ведения судейского протокола в реальном времени;
- автоматического расчета очков, сетов и победителя по официальным правилам Showdown;
- фиксации предупреждений, штрафов, тайм-аутов, смен сторон и иных судейских событий;
- надежного сохранения данных турнира и восстановления после сбоя;
- формирования итогового текстового отчета по турниру;
- полноценной работы без мыши, с клавиатуры и со screen reader.

Ключевое назначение первой версии: дать судье или секретарю соревнований простой, быстрый и доступный инструмент для ведения турнира и live-scoring матча по Showdown.

2. ОСНОВАНИЕ ДЛЯ РАЗРАБОТКИ

Логика приложения должна соответствовать официальным правилам IBSA Showdown Rules 2022-2025, в частности разделам о матче, игре с ограничением времени, жеребьевке, подачах, подсчете очков, потере мяча, тайм-аутах, смене сторон, предупреждениях и штрафах.

Приоритет источников правил:
1) официальный регламент и правила Showdown IBSA;
2) настройки конкретного турнира, если турнир не является санкционированным IBSA и организатор официально применяет дополнительные локальные параметры;
3) пользовательские параметры только в специально включаемом нестандартном режиме.

Стандартный режим приложения обязан реализовывать именно официальную логику Showdown, без упрощений и без подмены терминов неофициальными правилами.

3. ТИП И ГРАНИЦЫ СИСТЕМЫ

3.1. Тип приложения
- desktop application for Windows;
- работа офлайн, без обязательного подключения к интернету;
- локальное хранение данных турниров;
- запуск из portable-папки.

3.2. Границы первой версии
В первую версию обязательно входят:
- создание турнира;
- учет игроков;
- ручное создание матчей;
- live scoring матча;
- журнал событий;
- сохранение/восстановление;
- экспорт итогового TXT-отчета.

В первую версию не обязательно включать:
- сложную автоматическую жеребьевку;
- публикацию в интернет;
- облачную синхронизацию;
- веб-интерфейс;
- платежи, регистрацию через сайт, личные кабинеты;
- видеотрансляцию;
- статистику по ударам и траекториям.

4. ТЕХНОЛОГИЧЕСКИЕ ТРЕБОВАНИЯ

4.1. Платформа и поставка
- язык разработки: Python;
- ОС: Windows 10/11 x64;
- формат поставки: portable .exe;
- установка Python на компьютере пользователя не требуется;
- упаковка: standalone build через PyInstaller или эквивалентный механизм;
- приложение должно запускаться с флешки и из обычной пользовательской папки без прав администратора.

4.2. Работа с файлами
- все рабочие данные приложения должны храниться рядом с приложением или в подкаталоге data;
- отчеты должны сохраняться в подкаталог reports либо рядом с .exe, в зависимости от настройки;
- путь сохранения должен быть доступен для изменения в настройках.

5. ЦЕЛЕВАЯ АУДИТОРИЯ

Основные пользователи:
- судьи по Showdown;
- секретари соревнований;
- организаторы турниров;
- незрячие и слабовидящие пользователи;
- ассистенты судей и волонтеры, ведущие протокол матча.

6. ОБЩАЯ КОНЦЕПЦИЯ И ПРИНЦИПЫ UX

6.1. Общая концепция
Приложение должно быть максимально понятным, линейным и быстрым в работе. Во время матча пользователь не должен искать команды в сложных меню. Все наиболее частые действия должны быть доступны сразу, с клавиатуры, с понятными названиями и однозначным результатом.

6.2. Основные UX-принципы
- один экран — одна основная задача;
- фокус всегда предсказуем;
- экранный диктор должен получать понятные имена элементов и статусов;
- действия на матче должны требовать минимального числа нажатий;
- терминология в интерфейсе должна соответствовать правилам Showdown;
- опасные операции должны требовать подтверждения;
- приложение не должно заставлять пользователя пользоваться мышью.

6.3. Основной пользовательский сценарий
1. Запустить приложение.
2. Создать или открыть турнир.
3. Заполнить параметры турнира.
4. Добавить игроков.
5. Создать матч.
6. Открыть экран ведения матча.
7. Во время игры фиксировать голы, игровые ошибки, предупреждения, штрафы, тайм-ауты, смены сторон и иные события.
8. Завершить матч.
9. После окончания турнира сформировать итоговый TXT-отчет.

7. НОРМАТИВНАЯ ЛОГИКА SHOWDOWN, ОБЯЗАТЕЛЬНАЯ К РЕАЛИЗАЦИИ

7.1. Формат игры
В стандартном режиме приложение должно поддерживать игры из:
- 1 сета;
- 3 сетов;
- 5 сетов.

Победитель игры определяется так:
- в игре из 1 сета — победа после 1 выигранного сета;
- в игре из 3 сетов — победа после 2 выигранных сетов;
- в игре из 5 сетов — победа после 3 выигранных сетов.

7.2. Победа в сете
Сет считается выигранным, если игрок:
- набрал не менее 11 очков;
- имеет преимущество не менее 2 очков.

Примеры:
- 11:5 — сет завершен;
- 11:10 — сет не завершен;
- 12:10 — сет завершен;
- 15:14 — сет не завершен;
- 16:14 — сет завершен.

7.3. Подачи
- в начале каждого сета право первой подачи чередуется;
- каждый игрок выполняет по 2 подачи подряд;
- приложение обязано автоматически вести текущего подающего;
- приложение обязано отображать и озвучивать номер подачи в серии: первая или вторая.

7.4. Начало и возобновление игры
Приложение должно поддерживать судейскую последовательность состояния:
- подтверждение готовности игроков;
- объявление счета;
- объявление номера подачи;
- начало розыгрыша.

В интерфейсе не требуется воспроизводить свисток, но требуется корректно вести состояние игры и различать:
- игра идет;
- игра остановлена;
- тайм-аут;
- смена сторон;
- медицинский тайм-аут;
- судейский тайм-аут;
- сет завершен;
- матч завершен.

7.5. Официальные типы событий с начислением очков
В стандартном режиме должны использоваться следующие типы судейских событий.

7.5.1. Гол
Событие: Goal
Результат: 2 очка игроку, забившему гол.

7.5.2. Неправильная подача
Событие: Irregular serve / Неправильная подача
Результат: 1 очко сопернику.
Основания должны включать:
- более одного касания мяча ракеткой при подаче;
- подача позже чем через 2 секунды после сигнала судьи;
- подача до сигнала судьи;
- мяч перед подачей не находится на игровой поверхности;
- умышленное прокатывание мяча перед подачей;
- неправильный отскок от бокового борта при подаче.

7.5.3. Центральный экран
Событие: Center board / Центральный экран
Результат: 1 очко сопернику.
Основание: мяч прошел над экраном либо попал в экран с ошибкой по правилам.

7.5.4. Касание тела
Событие: Body touch / Касание тела
Результат: 1 очко сопернику.
Основание: мяч касается любой части тела, кроме игровой руки в перчатке.

7.5.5. Неправильная защита
Событие: Illegal defense / Неправильная защита
Результат: 1 очко сопернику.
Основание: запрещенное касание мяча в зоне ворот.

Особый случай: если мяч после касания в пределах площади ворот уходит прямо в ворота, это должно фиксироваться как гол соперника с начислением 2 очков, а не как обычная ошибка на 1 очко.

7.5.6. Аут
Событие: Out / Аут
Результат: 1 очко сопернику.
Основания:
- мяч покидает игровую поверхность после удара;
- мяч касается верхней части контактной планки.

7.5.7. Нарушение
Событие: Infringement / Нарушение
Результат: 1 очко сопернику.
Основания:
- неигровая рука находится внутри игровой зоны, кроме допустимого перехвата ракетки;
- неигровой рукой захватывается контактная планка в запрещенной области.

7.5.8. Нарушение ракеткой
Событие: Bat infraction / Нарушение ракеткой
Результат: 1 очко сопернику.
Основания:
- игрок не держит ракетку одной рукой, кроме смены игровой руки;
- игрок роняет ракетку.

7.5.9. Нарушение мячом
Событие: Ball infraction / Нарушение мячом
Результат: 1 очко сопернику.
Основание: игрок задерживает или останавливает мяч более чем на 2 секунды, и мяч не слышен сопернику.

7.6. События без начисления очков
Приложение обязано поддерживать следующие официальные события без прямого начисления очков:
- потеря мяча;
- повторная подача;
- поломка мяча;
- поломка ракетки;
- судейский тайм-аут;
- медицинский тайм-аут;
- предупреждение;
- смена сторон;
- окончание сета;
- окончание матча.

7.6.1. Потеря мяча
Событие: Lost ball / Потеря мяча
Результат: очки не начисляются, игра возобновляется повторной подачей.
Основания:
- мяч движется настолько медленно, что игрок не сможет его доиграть;
- игрок не слышит мяч и не может его найти;
- мяч не слышен более 2 секунд.

7.6.2. Поломка ракетки
Если ракетка ломается во время розыгрыша:
- игра останавливается;
- после замены ракетки выполняется повторная подача;
- очки, набранные после момента фактической поломки, не засчитываются.

7.6.3. Поломка мяча
Если мяч ломается во время игры:
- игра останавливается;
- мяч заменяется;
- игра возобновляется повторной подачей.

7.6.4. Повторная подача по решению судьи
Приложение должно поддерживать судейское событие «повторная подача» без изменения счета, в том числе когда судья не уверен в оценке эпизода либо игра была остановлена в момент, когда мяч был в игре.

7.7. Тайм-ауты
7.7.1. Игровой тайм-аут игрока
- каждый игрок имеет право на 1 тайм-аут продолжительностью 60 секунд в каждом сете;
- запрос возможен только в остановке игры;
- тайм-аут может запросить игрок или тренер;
- за 15 секунд до окончания тайм-аута должно формироваться уведомление «15 секунд».

7.7.2. Судейский тайм-аут
- может быть объявлен судьей при необходимости;
- если игра была остановлена в момент розыгрыша, возобновление происходит с повторной подачи.

7.7.3. Медицинский тайм-аут
- может быть объявлен судьей при травме игрока;
- предельное время до готовности игрока — 5 минут;
- если игрок не готов в течение этого времени, игра завершается поражением по умолчанию.

7.8. Смена сторон
- после каждого завершенного сета смена сторон обязательна;
- в третьем сете игры смена сторон производится после того, как любой из игроков наберет 6 очков, либо по истечении половины игрового времени, если игра ведется с лимитом времени;
- если игра состоит из 1 сета, смена сторон производится после того, как любой из игроков наберет 6 очков, либо по истечении половины времени сета при игре с лимитом времени;
- продолжительность смены сторон — 60 секунд;
- за 15 секунд до конца смены сторон приложение должно выдавать уведомление «15 секунд».

Приложение должно:
- автоматически подсказывать момент обязательной смены сторон;
- требовать подтверждение, что смена выполнена;
- фиксировать событие в журнале.

7.9. Ограничение времени
В стандартном режиме IBSA ограничение времени должно быть отключено и недоступно по умолчанию.

Для пользовательских или локальных турниров приложение должно поддерживать дополнительный режим игры с лимитом времени:
- организатор задает лимит времени на сет;
- часы должны останавливаться во время тайм-аутов, смены сторон и иных остановок игры;
- по истечении времени победителем сета объявляется игрок с большим количеством очков;
- если по истечении времени счет равный, приложение должно поддерживать специальный режим «решающее следующее очко после определения подающего».

7.10. Предупреждения, штрафы и поражение по умолчанию
7.10.1. Общие правила
- судья может вынести предупреждение или назначить штраф в любое время;
- если санкция вынесена во время розыгрыша, игра после этого возобновляется повторной подачей;
- если санкция вынесена в остановке игры, игра продолжается следующей подачей;
- предупреждения действуют на протяжении всей игры, а не только текущего сета.

7.10.2. Нарушения с системой «сначала предупреждение, затем штрафы»
Для группы нарушений, предусмотренных правилами 19.3, приложение обязано поддерживать следующую логику:
- первое нарушение — предупреждение;
- второе и каждое последующее нарушение — штраф 2 очка сопернику;
- повторное нарушение ведет к штрафу даже тогда, когда новое нарушение относится к другому подпункту этой же группы.

В приложении должны быть доступны как минимум следующие нарушения этой группы:
- игра сбоку от стола;
- запрещенное касание частей стола неигровой рукой;
- захват или удержание мяча пальцами игровой руки;
- чрезмерное или постоянное толкание стола;
- шумовые помехи ракеткой;
- разговоры во время игры или перерыва, кроме разрешенных правилами случаев;
- помещение части тела в область ворот снаружи;
- игра без касания пола хотя бы одной ногой;
- иные действия, квалифицируемые судьей как помеха, затягивание игры и т.п.

7.10.3. Штрафы без предварительного предупреждения
Приложение обязано поддерживать немедленный штраф 2 очка сопернику для следующих событий:
- касание маски без разрешения судьи;
- сигнал мобильного телефона или иного электронного устройства игрока или тренера во время игры;
- подсказки тренера игроку во время игры.

Для события с подсказками тренера в журнале должна быть отдельная отметка, что тренер подлежит удалению из игровой комнаты.

7.10.4. Поражение по умолчанию
Приложение обязано поддерживать завершение игры с результатом «поражение по умолчанию» как минимум в следующих случаях:
- серьезное нарушение игрока: оскорбление судьи, бросок мяча или ракетки и аналогичные действия;
- неявка или опоздание более чем на 5 минут;
- игрок не готов продолжить после медицинского тайм-аута или разрешенного выхода.

7.11. Разминка и предматчевые процедуры
Для полноты судейского протокола приложение должно поддерживать необязательные предматчевые события:
- жеребьевка;
- выбор первой подачи;
- начало и окончание разминки;
- пропуск разминки по взаимному согласию.

Для первой версии эти события могут быть реализованы упрощенно, но структура данных и журнал должны позволять их фиксировать.

8. РЕЖИМЫ РАБОТЫ ПРИЛОЖЕНИЯ

8.1. Стандартный режим IBSA
В этом режиме:
- все официальные правила фиксированы;
- изменение логики начисления очков запрещено;
- ограничение времени по умолчанию выключено;
- приложение использует официальные типы событий и их последствия.

8.2. Пользовательский режим
В этом режиме допускается:
- включение лимита времени;
- изменение названий некоторых пользовательских событий;
- добавление собственных заметок организатора.

При этом пользовательский режим не должен ломать базовую модель данных, журнал событий и экспорт отчетов.

9. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ ПО ЭКРАНАМ

9.1. Главный экран
Элементы:
- Создать новый турнир;
- Открыть турнир;
- Горячие клавиши;
- Настройки;
- Выход.

Поведение:
- при открытии фокус стоит на кнопке «Создать новый турнир»;
- переход по элементам — Tab и Shift+Tab;
- Enter активирует элемент;
- Escape закрывает модальное окно;
- screen reader озвучивает название окна и текущий элемент.

9.2. Экран создания турнира
Поля:
- название турнира;
- дата турнира;
- место проведения;
- формат турнира: круговой / олимпийская сетка / групповой этап + плей-офф / другой;
- формат игры: 1 / 3 / 5 сетов;
- режим правил: стандартный IBSA / пользовательский;
- использовать ограничение времени: да / нет;
- лимит времени на сет в минутах, если опция включена;
- путь сохранения отчетов;
- комментарий организатора.

Логика:
- название турнира обязательно;
- дата по умолчанию — текущая;
- в стандартном режиме редактирование логики очков запрещено;
- при включении лимита времени пользователь должен получить явное предупреждение, что это нестандартный режим для несанкционированных IBSA турниров.

9.3. Экран игроков
Возможности:
- добавление игрока;
- редактирование;
- удаление;
- изменение статуса;
- импорт списка игроков из TXT/CSV;
- переход к матчам.

Поля карточки игрока:
- ФИО;
- страна, клуб или организация;
- город;
- пол;
- дата рождения, необязательно;
- комментарий, необязательно;
- статус: активный / снялся / дисквалифицирован / не допущен.

Требования:
- список игроков должен быть доступен для screen reader как таблица или список;
- каждая строка должна озвучиваться полно и однозначно;
- удаление только через подтверждение;
- удаление игрока, уже участвующего в матчах, должно либо запрещаться, либо переводиться в мягкое архивирование со ссылочной целостностью.

9.4. Экран матчей турнира
Возможности:
- создать матч;
- выбрать игрока A и игрока B;
- указать стадию;
- указать номер стола;
- указать судью;
- указать секретаря;
- открыть матч в live scoring;
- удалить матч;
- завершить матч вручную с особой причиной;
- сформировать отчет.

Требования:
- в первой версии допустимо только ручное создание пар;
- автоматическая жеребьевка является дополнительной функцией;
- матч не может быть создан с одинаковым игроком в обеих ролях;
- статус матча: не начат / идет / приостановлен / завершен / завершен по умолчанию / отменен.

10. ЭКРАН ВЕДЕНИЯ МАТЧА

10.1. Назначение
Это главный рабочий экран. Он должен обеспечивать максимально быстрый ввод событий при минимальном количестве действий.

10.2. Состав блока информации
На экране должны быть явно отображены и доступны screen reader следующие поля:
- название турнира;
- стадия турнира;
- игрок слева;
- игрок справа;
- текущий сет;
- счет по сетам;
- текущий счет в сете;
- кто подает;
- номер подачи в серии;
- текущий статус игры;
- остаток времени тайм-аута или смены сторон, если запущен таймер;
- признак стандартного или пользовательского режима.

10.3. Быстрые кнопки основных событий
Для каждого игрока должны быть доступны крупные и однозначные кнопки:
- Гол игрока A (+2);
- Гол игрока B (+2);
- Ошибка игрока A, +1 игроку B;
- Ошибка игрока B, +1 игроку A;
- Штраф игроку A, +2 игроку B;
- Штраф игроку B, +2 игроку A;
- Предупреждение игроку A;
- Предупреждение игроку B;
- Тайм-аут игрока A;
- Тайм-аут игрока B;
- Судейский тайм-аут;
- Медицинский тайм-аут;
- Смена сторон;
- Повторная подача;
- Потеря мяча;
- Завершить сет;
- Завершить матч;
- Поражение по умолчанию игрока A;
- Поражение по умолчанию игрока B;
- Отменить последнее действие.

10.4. Простой и расширенный режим ввода
Должно быть два режима ввода:
- простой режим: быстрые кнопки без выбора детального подпункта;
- расширенный режим: выбор официального типа нарушения и, при необходимости, конкретной причины.

В расширенном режиме для событий ошибок должны быть доступны официальные категории:
- неправильная подача;
- центральный экран;
- касание тела;
- неправильная защита;
- аут;
- нарушение;
- нарушение ракеткой;
- нарушение мячом.

10.5. Журнал действий
Каждое действие фиксируется в хронологическом журнале.

Пример формата строки:
14:03:11 | Сет 1 | Гол | Игрок A | +2 | счет 2:0 | подача A, 2-я
14:03:48 | Сет 1 | Центральный экран | Игрок B | +1 Игроку A | счет 3:0
14:05:02 | Сет 1 | Тайм-аут игрока B | 60 сек
14:06:41 | Сет 1 | Предупреждение | Игрок A | основание: разговор во время игры

Журнал должен:
- быть доступен screen reader;
- поддерживать навигацию с клавиатуры;
- показывать текущее выделение;
- позволять открыть карточку события;
- поддерживать Undo минимум на 50 шагов;
- поддерживать Redo, если после Undo не была создана новая ветка истории.

11. БИЗНЕС-ЛОГИКА LIVE SCORING

11.1. Автоматические расчеты
После каждого события приложение должно автоматически пересчитывать:
- счет в текущем сете;
- счет по сетам;
- текущего подающего;
- номер подачи в серии;
- необходимость смены сторон;
- факт завершения сета;
- факт завершения игры.

11.2. Порядок применения события
Каждое событие должно обрабатываться транзакционно:
1. валидируется допустимость события в текущем состоянии;
2. создается запись журнала;
3. обновляется счет и состояние подачи;
4. проверяется окончание сета;
5. проверяется окончание игры;
6. данные немедленно сохраняются.

11.3. Ограничения и валидации
- нельзя начислить очки завершенному матчу без явного подтверждения возобновления;
- нельзя взять второй обычный тайм-аут игрока в том же сете без принудительного нестандартного подтверждения;
- нельзя выполнить смену сторон повторно без подтверждения корректировки протокола;
- нельзя изменить игрока матча после начала игры;
- события после завершения игры допускаются только как корректировка с обязательным логированием.

12. ТРЕБОВАНИЯ К ДОСТУПНОСТИ

12.1. Общие требования
Приложение должно быть пригодно для использования незрячим пользователем полностью без мыши.

12.2. Обязательные требования
- полная работа с клавиатуры;
- логичный и стабильный порядок Tab;
- понятные accessible name у всех интерактивных элементов;

- цвет не должен быть единственным носителем смысла;
- тексты кнопок должны быть буквальными и однозначными;
- озвучивание статуса должно быть информативным, но не избыточным.

12.3. Озвучиваемые статусы

17. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

17.1. Надежность
- ни одно событие не должно теряться при переходе между окнами;
- завершение матча требует подтверждения;

- открытие турнира до 200 игроков: не более 2 секунд;

- генерация TXT-отчета: до 5 секунд для турнира среднего размера.

17.3. Совместимость и переносимость
- Windows 10/11 x64;
- работа без Python;
- работа без интернета;
- отсутствие необходимости прав администратора.

17.4. Локализация
- первая версия интерфейса — русский язык;
- архитектура должна допускать последующее добавление английского языка.

20. КРИТЕРИИ ПРИЕМКИ

Приложение считается соответствующим ТЗ, если:
1. пользователь без мыши может создать турнир, добавить игроков, создать матч и провести игру;
2. в стандартном режиме логика подсчета соответствует правилам Showdown;
3. гол начисляет 2 очка;
4. официальные игровые ошибки начисляют 1 очко сопернику в соответствующих случаях;
5. штраф начисляет 2 очка сопернику;
6. предупреждения учитываются на протяжении всей игры;
7. второй и последующие проступки группы 19.3 корректно превращаются в штраф;
8. сет завершается только при достижении минимум 11 очков и разницы 2;
9. игра корректно завершается в форматах 1/3/5 сетов;
10. подача ведется сериями по 2, а первый подающий в сетах чередуется;
11. смена сторон корректно определяется по правилам;
12. тайм-ауты, предупреждения, штрафы и поражение по умолчанию корректно журналируются;
13. все интерактивные элементы доступны через клавиатуру;
14. NVDA и Narrator озвучивают основные элементы и статусы;
15. работает автосохранение и восстановление после сбоя;
16. формируется корректный TXT-отчет;
17. приложение запускается на Windows без установки Python.

Приоритет 3, можно отложить:
- автоматическая жеребьевка;
- расширенная турнирная аналитика;
- дополнительные форматы экспорта.

22. ИТОГОВАЯ ФОРМУЛИРОВКА ЗАДАЧИ ДЛЯ РАЗРАБОТЧИКА

Необходимо разработать portable Windows-приложение на Python для ведения турниров и судейского подсчета матчей по Showdown, ориентированное на незрячих и слабовидящих пользователей. Приложение должно обеспечивать создание турнира, учет игроков, создание матчей, live-ввод официальных игровых событий по правилам IBSA Showdown, автоматический расчет счета и победителя, журналирование всех судейских действий, автосохранение, восстановление после сбоя, полную клавиатурную доступность и формирование итогового TXT-отчета.
